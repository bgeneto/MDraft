# AsciiDoc is previewed by Asciidoctor.js in the webview, not by a second compiler

**Status:** accepted
**Superseded in part by:** `2026-10-18-asciimath.md` — the AsciiMath consequence no longer holds.
**Superseded in part by:** `2026-10-19-asciidoc-pandoc-export.md` — pandoc exports now receive Asciidoctor-rendered HTML, so the include and `:toc:` export gaps no longer hold.
**Date:** 2026-10-17

## Context

MDraft had three document languages and one preview path per language: `marked`
for Markdown, an external `typst` binary for Typst, and a sandboxed guest for
HTML. AsciiDoc was only an export target. Opening `.adoc` classified it as
Markdown, so `= Title` was a paragraph, `latexmath:[…]` was text, and every
AsciiDoc-only construct was lost.

The AsciiDoc implementation had to fit rules the other formats already follow:
no Rust parser for a markup language, no CDN, no second math library, no
network request at start-up, and no licensing machinery. It also had to stay out
of the startup bundle: the application starts in about a second and an extra
megabyte on every launch would be a visible regression.

`@asciidoctor/core` 4.1.1 is the current JavaScript Asciidoctor, a rewrite of the
Ruby processor. Its browser entry is 990,496 bytes uncompressed. The package's
`exports` map exposes only `"."`; the browser build is selected by Vite's
`browser` condition, not by a `/build/browser/index.js` subpath.

## Decision

AsciiDoc is rendered **in the webview** by `@asciidoctor/core`, dynamically
imported on the first AsciiDoc preview:

```ts
const Asciidoctor = await import("@asciidoctor/core");
```

The dependency is pinned exactly (`"@asciidoctor/core": "4.1.1"`), because 4.x
output and its extension API are still moving. The Asciidoctor chunk is lazy:
the startup chunk is 771,058 bytes and contains no Asciidoctor; the lazy chunk
is 990,496 bytes, with a 371,248-byte stylesheet-bearing sub-chunk.

The document is loaded with:

- `standalone: false` — the preview wants the body, not a document shell;
- `attributes: { showtitle: "" }` — embedded output sets `notitle`, and without
  this the document title disappears from the preview;
- `safe: "secure"` — attribute and include restrictions, and no source
  highlighter or icon font injection;
- `sourcemap: true` — `block.sourceLocation` drives the source anchors;
- `base_dir: document directory` — includes and relative assets resolve from
  the document, not the process;
- a **per-load** `Extensions.create()` registry. Nothing is global, so two
  renders cannot see each other's document directory.

The per-load registry carries:

1. An `IncludeProcessor` that reads a target through the existing
   `read_document` command, only after resolving it inside the document
   directory, with a cycle guard and nested resolution against the included
   file's directory. `http:`, `file:`, UNC, absolute and escaping `..` targets
   are refused and replaced by a visible unresolved-directive message. Include
   attributes (`lines`, `tag`, `leveloffset`) are not applied.
2. A `TreeProcessor` that gives every block with a main-file source location a
   unique `mdraft-line-<n>` role and records its start and end lines.

The marker roles are rewritten to `data-line` / `data-line-end` in the DOM after
DOMPurify, not by a string postprocessor: `convert_embedded` already adds a
document title, a `#toc` and footnotes that are not blocks, and a DOM pass is
safer than matching classes in generated markup. The document title is stamped
as line 1. `rebuildAnchors()` and the existing pane sync consume the result, so
AsciiDoc has no second synchroniser.

The converter output is sanitised with the Markdown preview's DOMPurify profile.
Inline `latexmath` arrives as plain `\(...\)` text and display math as
`.stemblock` containing `\[...\]`; `renderMathIn(host)` walks text nodes and
renders only those delimiters with KaTeX. `$...$` is left alone because
AsciiDoc uses it for AsciiMath. Listings are highlighted with the bundled
highlight.js, and a `mermaid` listing goes through the existing diagram pass.

The preview and export structure rules live twice: `src/styles.css` for the
preview, and `ASCIIDOC_CSS` in `markdown.ts` for `wrapStandaloneHtml` and
`wrapPrintHtml`, which never load the application stylesheet. Asciidoctor's own
stylesheet is not shipped or applied.

Pandoc export of an AsciiDoc buffer selects `-f asciidoc` through the same
reader-selection helper as HTML; the Markdown math extensions are removed.
Pandoc's AsciiDoc reader is known to resolve `include::` against its own working
directory and to leave `:toc:` empty, so those remain documented export gaps.

## Consequences

- AsciiDoc is a fourth first-class document language: `.adoc` and `.asciidoc`
  open, save, reload, appear in the Files panel, the default-extension select,
  the open/save filters, the outline and the paste destination, and get a
  preview with admonitions, listings, tables, local images, local includes,
  `:toc:`, KaTeX and scroll sync.
- The application gains one lazy chunk, not a second process and not a Rust
  parser. The startup bundle is unchanged in kind; the cost is paid on first
  preview and accepted.
- The document directory is the include jail. A document that includes a large
  book re-reads it on every preview pass, because there is no include cache;
  that is a deliberate simplicity trade and a measurement point.
- AsciiMath is not rendered. `stem:[…]` under the default `:stem:` remains
  text, and only `latexmath` becomes KaTeX.
- Pandoc exports of AsciiDoc are lossy for includes and `:toc:`. The native HTML
  and PDF exports use the preview and do not have that gap.
- The file format is not changed. There is no settings migration: an older
  `settings.json` loads, and a `.md`/`.typ`/`.html` document behaves exactly as
  it did before.
